Caso 03

SisBombastic

Sistema operativo y financiero · colaboración · Terminado

Un emprendimiento de coleccionismo no puede adivinar si gana o pierde. Hacía falta un sistema que uniera inventario, compras, ventas, caja y rentabilidad.

.NET Blazor SQL Server C#

Contexto

Bombastic Dreamers opera un negocio de coleccionismo: muchas SKU, compras irregulares, ventas por canal y una caja que no perdona el desorden. El día a día se sostenía con control manual. Colaboré en el análisis y el desarrollo del sistema; no soy el dueño del negocio.

Problema

Sin un modelo único, el inventario, las compras y las ventas viven en islas. Eso oculta el costo real de cada pieza, retrasa el cuadre de caja y hace imposible hablar de rentabilidad con números, no con sensación.

Mi participación

Participé en el análisis del flujo del negocio y en el desarrollo de los módulos que lo sostienen: inventario, compras, ventas, caja y una lectura de rentabilidad. El criterio fue el mismo que en un sistema institucional: el dato se captura una vez y se reutiliza en cada vista.

Proceso

  • Mapear cómo entra un producto, cómo se vende y cómo se cierra el día.
  • Diseñar el modelo relacional alrededor de producto, movimiento, comprobante y caja.
  • Construir la aplicación en el stack .NET / Blazor / SQL Server.
  • Priorizar las pantallas que el negocio usa todos los días, no un panel decorativo.

Arquitectura y datos

SQL Server como núcleo. La aplicación Blazor cubre operación diaria. El inventario no es una lista: es el resultado de compras, ventas y ajustes. La rentabilidad sale de cruzar costo, precio y movimiento, no de una celda suelta en una hoja de cálculo.

Resultado

El negocio pasó de operar a ciegas a tener un sistema que registra el ciclo completo. Inventario, caja y margen dejan de ser conversaciones aparte. Para mí, el valor está en haber traducido un oficio (coleccionismo) a un modelo que un operador puede usar sin ser programador.

Aprendizajes

En un emprendimiento el usuario es quien abre y cierra la tienda: si el flujo tiene un paso de más, no se usa. El análisis previo vale más que agregar pantallas. A futuro: reportes más finos por línea de producto y una auditoría más explícita de cada movimiento de caja.
