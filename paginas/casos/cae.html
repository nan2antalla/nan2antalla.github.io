Caso 02

CAE — Control de asistencia

Sistema empresarial · UTEPSA · Terminado

Carga masiva de tarjetas de estudiantes a los biométricos ZKTeco: primero por el DLL, después por la API. En el molinete, una pantalla muestra la foto de quien entra y de quien sale.

C# .NET ZKTeco DLL ZKTeco API

Contexto

En UTEPSA el acceso depende de biométricos ZKTeco. Los estudiantes se identifican con tarjeta. Si el lector no tiene al alumno —o todavía tiene a alguien que ya no debería entrar— el hardware no sirve. En portería tampoco basta el beep: hay que ver de quién se trata.

Problema

Había que actualizar muchos dispositivos a la vez y cargar tarjetas en masa. Hacerlo a mano no escala. Además hacía falta una vía por DLL y otra por API, según el dispositivo. En el molinete, el evento de entrada o salida tenía que verse: la foto, no un log.

Mi participación

Como asistente de programación TI desarrollé la actualización masiva de dispositivos ZKTeco: una vía por el DLL y otra por la API, para la carga de tarjetas de estudiantes. También la pantalla del molinete que muestra la foto al ingresar y al salir. El trabajo está entre el hardware, la lista de usuarios y una interfaz que se lee a distancia.

Proceso

  • Integrar el DLL de ZKTeco para actualizar de forma masiva los biométricos.
  • Añadir una segunda vía por la API de ZKTeco para la misma carga de tarjetas.
  • Cargar usuarios de forma asíncrona para no trabar la corrida si un lector tarda o falla.
  • Mantener lista blanca: elimina a quien no corresponde y añade a quien sí.
  • Exponer el avance en una ventana tipo consola.
  • Pantalla de molinete: foto de la persona en el ingreso y en la salida.

Arquitectura y datos

Lista de estudiantes en SQL Server → aplicación .NET que habla con ZKTeco por DLL o por API → biométricos actualizados en masa. La consola muestra la corrida. En el acceso, otra aplicación pinta la foto cuando alguien marca. Dos problemas distintos: poblar el hardware y hacer visible el evento en portería.

Resultado

Las tarjetas se cargan a los dispositivos sin ir uno por uno. Hay un camino por DLL y otro por API, según el caso. En el molinete se ve quién entra y quién sale. Para la universidad eso es control de acceso real: el dato llega al lector y la persona se reconoce en la puerta.

Aprendizajes

Con hardware el fallo es el caso normal: un lector caído no puede frenar al resto. Por eso la carga es masiva y asíncrona. La API y el DLL no son el mismo oficio: uno u otro, según lo que el dispositivo y la red permitan. La pantalla del molinete no es un dashboard: es una señal. Si la foto no se entiende al paso, no sirve.
